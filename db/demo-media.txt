# Studio files the demo carries: one line per camera angle, per take.
#
#   <stem><TAB><cuts>
#
# cuts is which of studioFilesMini/{raw,post} holds that angle. Both the .mp4
# and the .jpg thumbnail exist for every cut listed - production makes them
# together, and scripts/seed-demo-data.sh checks for both.
#
# The angles come from matched_transcriptions, which names them one column
# each: l_file, m_file, r_file, a_file, b_file. They are NOT the same stem with
# a different letter - the numeric suffix differs per angle within a take
# (M20260227_5998, L20260227_7582 and R20260227_0221 are one recording), so
# the mapping can only be read out of the row and never guessed from a
# filename. studioIndex api.php?page= returns exactly those five columns
# and its front end builds every URL from them.
#
# m_file is recorded with a .wav extension - the audio track the take was
# matched on - and every consumer swaps it for .mp4, or for .jpg when it wants
# the thumbnail. The stems here are already extension-free.
#
# A and B have no post cut on any of these takes. That is not a gap in the
# copy: production has A/B post cuts for other sessions but ran none for
# these, so studioIndex 404s on post/<A stem>.jpg there exactly as it does
# here, and falls back to the raw thumbnail by design (index.html img.onerror).
#
# Kept as a separate list, not derived from the SQL, so scripts/seed-demo-data.sh
# never has to parse SQL to know which files to move, and so a reviewer can see
# in one place exactly which recordings the demo carries.
#
# The files themselves live in the private repo signlab_demo-media, which
# scripts/repos.tsv deploys to /web/gebarenoverleg_media. This list and that
# repository have to agree: seed-demo-data.sh checks every line here against
# the checkout and refuses to seed if one is missing, so adding an angle means
# adding its files there first.
